# Sriver

**本地多模型调度引擎**——把多个 AI 模型并发调用、匿名盲审、选最优答案返回给前端。

---

## 先说清楚

Sriver 的代码是**用自然语言写出来的**。作者不写代码，靠对话让 AI 生成、修改、重构整个项目。逻辑判断、架构设计、报错定位，全部由作者主导。**这不是隐瞒，是坦白。**

如果你在意"这是不是亲手敲的"——那 Sriver 可能不适合你。如果你在意"这东西能不能用、解决了什么问题"——那继续看。

---

## Sriver 是干什么的

你平时用一个 AI 聊天。它可能回答得挺好，也可能跑偏、偷懒、答非所问。**你没法对比，只能认了。**

Sriver 换个思路：**你要一个答案，它让 4 个 AI 同时写。**

- 有的模型擅长叙事，有的擅长逻辑，有的更懂角色扮演
- 它们各写一份草稿
- 一份独立的裁判模型**匿名盲审**，不知道哪份是谁写的
- 代码规则 + 裁判评分加权，**选最优的一份**递给你

你看到的还是一个 AI 在回答。实际上背后是一个"董事会"替你对比、投票、选优。

**它的本质是一个本地代理**——装在你手机上，RK（RikkaHub）或任何支持 OpenAI 接口的前端都能连它。它对外长得像一个 AI，实际调度一群 AI。

---

## 几个你可能想知道的事

**不会用你的额度乱跑。** 模型挂了会自己踢出去冷却（默认 90 秒），裁判挂了自动降级到纯代码评分，主裁判挂了换备用裁判。**三层兜底，一个组件失败不会让你卡死。**

**有反馈闭环。** 消息第一行发 `ture` 触发——本轮结束后，每个模型会收到自己上一轮**缺点笔记**（只反馈低分项，不反馈优点）。下一轮它会注意规避。**保持多样性，不磨平风格。**

**你可以随时掌控。** `/models` 手动指定模型、`/only` 临时限制、`/judge` 临时换裁判、`/调试` 开关 debug。**不用改配置文件。**

**你的 API Key 只存在本地。** 配置在 `~/.sriver/config.json`，不上传任何地方。**Sriver 本身不联网（除了调用你自己配的端点）。**

## 快速开始

**环境要求：** Python 3.10+（Termux 用户可直接用系统 Python），**零第三方依赖**。

```bash
# 1. 放到家目录
cd ~

# 2. 启动
python3 -u ~/sriver.py
```

第一次启动会进入**三步配置向导**：

```
Step1：填端点信息（生成端 URL + Key，裁判端可复用）
Step2：选生成模型（输入编号，逗号分隔）
Step3：选裁判模型（或回复 SKIP 关闭裁判）
```

配置完成后，**新建一个对话**再开始用。

配置向导会写入 `~/.sriver/config.json`。想重来就发 `/重建`。

## 架构（从这里开始进入技术细节）

```
┌─────────────────┐
│  RK / 前端      │
│  (OpenAI 兼容)  │
└────────┬────────┘
         │ HTTP
         ▼
┌─────────────────────────────────────┐
│  Sriver (本地 7860 端口)            │
│                                     │
│  命令分发 → 并发调度 → 拒答过滤     │
│  → 匿名盲审 → 降级链 → 最优草稿     │
└─────────────────────────────────────┘
```

**三层降级：**

1. **主裁判失败** → 备用裁判接管
2. **裁判全部失败** → 纯代码规则评分
3. **模型连续失败 2 次** → 冷却 90 秒后自动回来

**模块结构（`sriver/` 目录）：**

```
sriver.py              启动器（5 行）
sriver/
  core.py              共用工具（拒答检测、代码打分、SYSTEM_PROMPT）
  runtime.py           运行时状态容器 RT
  config.py            配置加载 + 端点测试
  network.py           网络层（call_api / stream_model / 模型解析）
  judge.py             裁判逻辑 + 评分
  wizard.py            三步配置向导
  commands.py          命令解析
  logging_utils.py     日志
  stats.py             战绩 + 金句
  health.py            健康监控
  server.py            HTTP 处理 + 主流程
```

**每个模块 < 500 行，一个文件一件事。**

## 关键设计

**RT 单对象收全局。** 早期版本用 13 个模块级全局变量，跨函数改一处要写一串 `global` 声明。现在全收进 `runtime.RT` 一个对象，跨模块只需 `from .runtime import RT`。

**`call_api` 线程包装。** 裁判调用原本是同步阻塞的，用户取消也要等 15 秒超时。现在用线程包装 + 主线程轮询 `abort_event`——客户端一断连，立刻返回，不等上游。

**`do_POST` 拆分。** 主流程从最初的 428 行拆成三个函数：`_handle_command`（命令分发）、`_run_generation`（并发调度）、`_run_judging`（裁判打分）。`do_POST` 本身只剩 140 行。

## 配置

配置文件在 `~/.sriver/config.json`，首次运行向导自动生成。

**完整字段说明见 `config.example.json`。** 关键项：

| 字段 | 说明 |
|------|------|
| `gen_api_base` / `gen_api_key` | 生成端端点 |
| `judge_api_base` / `judge_api_key` | 裁判端端点（可复用生成端） |
| `smart_keywords` | 自动匹配生成模型的关键字 |
| `judge_keywords` | 自动匹配裁判的关键字 |
| `max_concurrency` | 并发数（建议 2-3） |
| `max_models_per_round` | 每轮最多模型数 |
| `gen_timeout` / `judge_timeout` | 生成/裁判超时（秒） |
| `feedback_trigger` | 反馈触发词（默认 `ture`） |
| `server_port` | 监听端口（默认 7860） |

## 已知边界

- **单本地用户设计。** 多个局域网客户端同时连向导会互相覆盖。
- **裁判阶段取消不能秒停。** 已用线程包装优化到"不等上游"，但裁判已在处理中的请求仍会跑完当前这一份。
- **`reasoning_content` 依赖上游。** 代码支持透传思考过程，但只有部分模型返回。这不是 Sriver 的问题。
- **测试不覆盖网络层。** 61 个测试全部是纯函数，`do_POST` / `call_api` 这些核心路径靠 `smoke.sh` 真机验证。
